Q1What is the difference between lexical retrieval and semantic retrieval, and when would you choose each?

AspectLexical RetrievalSemantic Retrieval
MatchingExact term / keyword matching (e.g., BM25, TF-IDF)Meaning-based matching using embeddings (e.g., cosine similarity)
StrengthsHigh precision, handles rare terms, fast, interpretableCaptures intent and context, works with paraphrases
WeaknessesMisses semantic meaning (synonyms, rephrased queries)May miss exact terms, needs embeddings and more compute
Best ForProduct search, technical docs, IDs, legal termsOpen-ended queries, Q&A, knowledge search, RAG
When to Choose Which? Use Lexical Retrieval when exact terms and precision matter (e.g., IDs, product codes). Use Semantic Retrieval when you need to capture meaning, intent, or paraphrased queries (e.g., RAG, natural language questions).

Q2How does BM25 calculate document relevance, and what limitations does it have?

BM25 (Best Matching 25) is a lexical ranking algorithm that scores a document based on term frequency, term rarity, and document length normalization.

Score(D, Q) = Σ IDF(t) × [TF(t, D) × (k₁ + 1)] / [TF(t, D) + k₁ × (1 - b + b × |D| / avgdl)]

TF(t, D) = Frequency of term t in document D
IDF(t) = Rarity of term t (higher for rare terms)
|D| = Length of document D
avgdl = Average document length in the corpus
k₁, b = Tunable parameters (typically k₁ = 1.2-2.0, b = 0.75)
Limitations of BM25: No semantic understanding (misses synonyms, paraphrases). Relies on exact term matching (lexical overlap). Struggles with long, complex queries. Limited for domain-specific or context-heavy search.
QueryHigh BM25 ScoreLow BM25 Score
"blood pressure medication"Docs with exact terms "blood pressure" and "medication"Docs with paraphrase "to control hypertension" (missing exact terms)

Q3How would you choose between sparse embeddings and dense embeddings for a domain-specific search system?

Sparse EmbeddingsDense Embeddings
RepresentationHigh-dimensional, mostly zero vectors (e.g., BM25, SPLADE)Low-dimensional, dense vectors (e.g., BERT, E5, Sentence-BERT)

Use Hybrid When: You need both lexical accuracy and semantic recall. The domain has mixed queries (e.g., product + intent).

Q4How do bi-encoders generate embeddings for retrieval, and why are they preferred for large-scale search?

A bi-encoder uses two separate encoders (or a shared encoder) to convert the query and document into dense embeddings in the same vector space, and retrieves using a fast similarity score (e.g., cosine similarity).

Why Preferred at Scale
Efficiency: Fast vector search (ANN, sub-second). Scalable: Handles millions to billions of documents. Cost-Effective: Embeddings can be precomputed, indexed, and stored in a vector index (FAISS, HNSW, etc.). Production Ready: Works with vector databases (Pinecone, Milvus, etc.).
Architecture: Query → Encoder → Embedding | Document → Encoder → Embedding | Similarity (cosine / dot) → Top-K Docs

Q5What is Approximate Nearest Neighbor (ANN) search, and how does it improve retrieval performance compared with exact search?

Exact Search (Brute Force)ANN Search
ComplexityO(N) — compares query with all vectorsO(log N) — uses an index to search a small, relevant subset
LatencyHigh (slow for large datasets)Low (real-time / sub-second)
ScalabilityPoor (doesn't scale well)High (scales to millions+ vectors)
Accuracy100% (exact neighbors)~95-99% (approximate, tunable)

ANN search finds the top-K most similar vectors with a huge gain in speed and scalability, trading a tiny bit of accuracy for low latency.

Common ANN Indexes: HNSW (graph-based, high quality), IVF (inverted file, partitions vectors into clusters), PQ (product quantization, compresses vectors to reduce memory & speed up search).

Q6Your search system performs well on semantic queries but misses exact product codes and technical identifiers. How would you solve this?

Solution: Hybrid Retrieval Pipeline — combines dense (semantic) and sparse (lexical) search so it can retrieve both meaning-based results and exact matches like product codes, SKUs, technical identifiers.

MethodQuery ("specs for router RT-AX88U")Result
Dense Only (semantic)May return general router specsMisses exact model
Sparse Only (lexical)May miss relevant context and variantsReturns exact model (RT-AX88U)
Hybrid (recommended)Returns exact model + relevant specs and docsBest of both worlds

Key Techniques:

  • Hybrid Search: Combines lexical and semantic retrieval
  • Entity & Code Detection: Identify product codes, SKUs, part numbers, etc.
  • Normalization: Keep codes as-is for lexical processing
  • Metadata Filters: Use structured fields (e.g., product category) for higher precision

Q7How does Reciprocal Rank Fusion (RRF) combine results from multiple retrieval systems, and why is it useful?

RRF (Reciprocal Rank Fusion) combines results from multiple retrieval systems (e.g., BM25 + dense search) by giving each document a score based on its rank in each list and summing those scores.

RRF Score Formula:
RRF(d) = Σ 1 / (k + rankᵢ(d))

d = document
n = number of retrieval systems
rankᵢ(d) = rank of d in the i-th result list
k = small constant (typically 60) to stabilize scores
BM25 ResultsDense ResultsRRF Score (k=60)
d1, d2, d3, d4, d5d3, d1, d4, d2, d5d1: 1/61+1/62=0.0328 | d2: 1/62+1/64=0.0317 | d3: 1/63+1/61=0.0325 | d4: 1/64+1/63=0.0313 | d5: 1/65+1/65=0.0308
Why RRF? Simple, effective, and model-agnostic. Improves recall and ranking robustness. Works well in hybrid and production systems without model training.

Q8What is the difference between a bi-encoder and a cross-encoder, and how would you use both in a retrieval pipeline?

Bi-EncoderCross-Encoder
ArchitectureEncodes query and document separately (q and d)Encodes query and document together ([q; d])
OutputSimilarity (e.g., cosine / dot)Direct relevance score (0-1) from the model
SpeedFast and scalableSlower (more compute)
AccuracyGood (high recall)Higher (better relevance)
Best UseLarge-scale candidate retrieval (e.g., top-100 / top-1,000)Re-ranking a small set (e.g., top-10 / top-50)

Combined Retrieval Pipeline (Recommended):

  1. Candidate Retrieval (Bi-encoder): Retrieve Top-K (K = 100-1,000) — High recall, Better latency
  2. Re-ranking (Cross-encoder): Re-rank Top-K (K = 10-50) — Better relevance, Balanced latency & cost

Q9Your retriever returns relevant documents, but the most useful ones appear too low in the results. How would you improve ranking?

I'd improve ranking by using a stronger re-ranking model (e.g., cross-encoder), adding quality signals (metadata, recency, authority), leveraging hybrid retrieval, and tuning the scoring strategy to better capture relevance.

Ways to Improve Ranking:

  • Re-ranking: Apply a cross-encoder or LLM re-ranker on top-K results for better relevance
  • Hybrid Retrieval: Combine BM25 (lexical) + dense retrieval (semantic) to improve recall and ranking quality
  • Better Signals: Incorporate metadata, recency, source authority, click-throughs, and document quality
  • Query & Chunk Optimization: Refine query (rewrite/expand) and use meaningful chunking for more relevant matches
  • Learning-to-Rank: Train a ranker (e.g., LambdaMART) using user feedback or labeled relevance data
Practical Tips: Tune the Top-K and scoring weights. Add domain-specific metadata filters. Avoid very small or noisy chunks. Use evaluation (nDCG, MRR) to validate ranking improvements.

Q10How would you determine the optimal Top-K value for a retrieval system without increasing unnecessary context?

Approach: Evaluate retrieval quality (e.g., Recall@K, nDCG) across different K values (e.g., 5, 10, 20, 50) and choose the point where performance saturates — the "elbow" where gains become marginal.

Q11How do similarity thresholds and metadata filters affect retrieval quality, and how would you tune them?

Similarity thresholds filter results by a minimum similarity score (e.g., ≥ 0.75). Metadata filters restrict results using structured fields (e.g., date, source, category).

Similarity ThresholdMetadata Filters
EffectHigher threshold → higher precision, lower recall. Lower threshold → higher recall, but more noise.Improves relevance and reduces irrelevant matches. Especially useful in multi-domain or large corpora.

Example: Threshold Tuning

Key Takeaways: Tune threshold to balance precision and recall. Use metadata filters to improve relevance and efficiency. Validate with offline metrics and A/B testing.

Q12How would you implement query expansion or query rewriting to improve retrieval when users submit vague or ambiguous questions?

I'd improve retrieval by rewriting or expanding the query to a clearer form, adding relevant terms, synonyms, and past context. This helps bridge the gap between the user's intent and the language used in the documents, leading to higher relevance.

Workflow: Query Rewriting & Expansion

User Query → LLM Rewrite → "setup guide for ASUS RT-AX88U router"
                    ↓
            Expansion → "configuration, install, quick start, manual"
                    ↓
            Searchable Queries

Techniques for Better Queries:

  • Query Normalization: Fix spelling, case, formats (e.g., "LLM's" → "LLM")
  • Query Expansion: Add synonyms, abbreviations, related terms (e.g., "RAG" → "Retrieval Augmented Generation")
  • Domain Enrichment: Use entity aliases, or domain-specific terms into explicit, searchable queries
  • LLM Rewrite: Use an LLM to rewrite the query to a clearer, intent-focused form
Example: Original: "laptop overheating" → Limited matches, misses variants. Rewritten/Expanded: "laptop overheating fix, high temperature, thermal issue, cooling" → Retrieves more relevant documents.

Q13What is multi-stage retrieval, and how would you design a pipeline that combines candidate generation, filtering, and re-ranking?

Multi-stage retrieval is a retrieval strategy that retrieves candidates in multiple steps — first a fast and wide recall, then filtering, and finally a more accurate re-ranking.

Pipeline Design:

  1. Candidate Generation: Retrieve a large set (e.g., top-1,000) using BM25 + dense (hybrid)
  2. Filtering: Apply metadata filters, threshold, and remove duplicates
  3. Re-ranking: Re-rank (e.g., top-50) with Cross-encoder (higher precision)
  4. Output: Return final top-K (e.g., 5-20) for the LLM or user
MethodK (Example)
Candidate Generation (BM25+Dense)1,000
Filtering (Metadata+Rules)100
Re-ranking (Cross-Encoder)10-20
Benefits: Higher relevance (better ranking). Scalable and cost-efficient (heavy models only on few docs). Balances recall, precision, and latency.

Q14Your RAG system retrieves documents containing the correct information, but the LLM fails to use them properly. How would you investigate the problem?

Investigation Checklist — run step-by-step through the RAG pipeline to find where the information is getting lost.

StepCheckCommon Causes & Fixes
1. Verify RetrievalDo the top-K docs actually contain the required information?Relevant docs missing → Improve retrieval (hybrid, re-rankers, chunking)
2. Check Context WindowIs the information getting lost in too much context?Too much noise → Re-rank and pass only the most relevant chunks
3. Review PromptDoes the prompt instruct the model to use only this context?Model hallucination → Add grounding instructions, use a more capable model
4. Analyze Model BehaviorLook for instruction-following issues, hallucination, or context ignoringPrompt issues → Fix prompt, add examples, use structured output
5. Fix & TestAdjust chunk size, prompt, or re-ranking and validate with generation metricsIterate based on the problem
Key Takeaway: Fix the issue at the right layer — retrieval, context, prompt, or model — based on where the problem actually is.

Q15How would you design a retrieval system for large documents containing tables, structured data, and multiple content types?

I'd design a multi-modal, structure-aware retrieval system that extracts and indexes different content types (text, tables, figures) separately while preserving relationships.

Architecture: Multi-modal Search for Complex Documents

  1. Document Parsing: Extract text, tables, figures (e.g., Unstructured, LlamaParse)
  2. Content-specific Chunking Strategy: Text chunks, table embeddings (TaBERT, TUR), figure embeddings by region
  3. Metadata & Linking: Store type, page, section, and relationships
  4. Appropriate Embeddings: Text embeddings (BGE, OpenAI), table embeddings, figure embeddings
  5. Retrieval & Re-ranking: BM25 + dense hybrid with cross-encoder re-ranking
Key Takeaway: Use a structure-aware, multi-modal retrieval pipeline to handle text, tables, and other content types reliably.

Q16How would you handle out-of-vocabulary (OOV) and rare queries in a retrieval system?

OOV and rare queries occur in real-world systems and can degrade retrieval quality. I'd use a combination of query expansion, subword models, character-level matching, and fallback strategies.

TechniqueHow It WorksRecallPrecision
Query ExpansionSynonyms, related terms, LLM rewrite↑ Increases Recall↓ May decrease
Subword ModelsBPE, WordPiece, character n-grams↑ Handles unknown words↑ Maintains Precision
Character-Level MatchingFuzzy, edit distance↑ Handles typos, new names↓ Filters irrelevant results
Fallback StrategiesLexical + semantic hybrid↑ Best coverage↑ Balanced

Example: OOV Query Handling

QueryTechniqueResult
"XGBoost model" (rare term)Expansion: xgboost, xg boost, gradient boosting, machine learningMore matches
Subword: xg + boost (BPE / WordPiece)Handles unknown tokens
Lexical Fallback: BM25 match on related termsWorks for new product names, codes
Semantic: Embedding search for contextCaptures meaning
Key Takeaway: Combine multiple techniques — no single method is enough for OOV and rare queries.

Q17How would you design a retrieval system for real-time or streaming data?

I'd use incremental indexing, streaming pipelines, and continuous updates to keep retrieval fresh, fast, and scalable while handling high query volume.

Key Design Considerations:

  • Low Latency: Near real-time updates
  • Data Freshness: Support continuous updates
  • Scalability: Handle high query volume
  • Fault Tolerance: Retries, monitoring
  • Event-Driven Updates: Automate index refresh

Q18How Do You Handle Out-of-Vocabulary (OOV) Queries and Rare Terms in Retrieval?

OOV Handling Workflow — Combine query normalization, expansion and hybrid retrieval to handle unseen, rare or domain-specific terms.

Key Techniques:

  • Query Normalization: Fix spelling, case, formats (e.g., "LLM's" → "LLM") to handle unseen words
  • Query Expansion: Add synonyms, abbreviations, related terms (e.g., "RAG" → "Retrieval Augmented Generation") for better coverage
  • Subword Models: Use BPE / WordPiece to handle unknown tokens
  • Hybrid Retrieval: Use lexical (BM25) and semantic (embeddings) for better coverage
Workflow: OOV / Rare Query → Normalization → Expansion → Subword Models → Hybrid Retrieval (lexical + semantic) → Results

Q19How Do You Monitor and Improve Retrieval Performance in Production Over Time?

Production Retrieval Monitoring Loop — Track retrieval metrics, analyze failures, and use continuous data and user feedback to improve relevance.

Continuous Improvement Loop:

  1. Monitor: Track metrics (Recall@K, MRR, Latency)
  2. Analyze: Find failing queries (where results are wrong)
  3. Update: Refresh data, retrain rankers, tune thresholds, re-index
  4. Validate: A/B test improvements, monitor business metrics
Key Metrics to Track: Recall@K, MRR (Mean Reciprocal Rank), nDCG, Latency (p50, p99), Query Volume, Error Rates, User Feedback Signals (clicks, dwell time, explicit feedback).
